04 · F0：文件里保存了经验，模型就“学会”了吗？

不一定。这里要分开两件事：训练可以改变模型参数；把偏好或规则写进文件，改变的是模型可以读取的外部信息。文件存在，并不代表每次回答都会用到它。

例子：周报先写结论

把“周报先写结论”保存为规则 → 下次写周报时读到这条规则 → 放入当前上下文 → 按规则生成 → 检查是否执行。若只完成第一步，后续仍可能没有效果。

因此，经验积累包括保存、召回、使用和维护。错误或过期的规则需要更新，不能只靠不断增加文件。阅读 F0 详细导读与自测 →

05 · F1：模型回答错了，应该先检查什么？

模型根据上下文生成文字，流畅的表达本身不是事实依据。遇到不可靠回答时，可以先分辨缺的是哪类信息：

  • 事实依据不足：关键说法有没有可核对的资料？
  • 信息过时：资料的日期、版本是否适合当前问题？
  • 背景缺失：模型是否知道本次任务所需的用户或业务条件？

例如，询问退货条件时，如果模型拿到的是旧政策，回答再清楚也可能不适用。补充当前政策后，还要继续核对它是否正确理解条款，而不是认为“有资料就一定对”。

Token 与上下文：Token 是模型处理文本的片段单位，与汉字数量没有固定对应关系。上下文像容量有限的工作台，要放入当前任务需要的信息；长聊天记录也不自动等于跨会话的持久记忆。阅读 F1 详细导读与自测 →

06 · F2：用一个退货场景串起四类能力

假设用户问：“这笔订单能退吗？如果可以，帮我申请。”这不只是回答知识题，还涉及查询、判断和行动。以下是概念示例，本次没有连接真实订单系统。

  1. 先找到依据（RAG）：检索当前有效的退货政策，把相关条款交给模型参考。
  2. 补足已有背景（Memory）：召回用户此前提供的订单背景，避免重复询问；订单当前状态仍需查询，不能把旧记录当作最新事实。
  3. 按流程处理（Skill）：先核对订单和条件，再解释判断依据，在需要时取得确认，最后提交申请并核对结果。
  4. 接入外部能力（MCP）：如果订单服务提供 MCP 接口，可通过统一协议暴露查询、申请等工具。MCP 负责接入规范，业务规则和权限仍要另行处理。

模型观察查询结果、决定下一步、调用工具，再观察返回结果，形成持续的任务循环。若申请失败，就需要根据错误继续处理，而不是只生成一句“已成功”。

这四项不是同一种东西，也不是每个 Agent 都必须全部具备。RAG 侧重找证据，Memory 侧重历史信息的保留与召回，Skill 侧重可复用方法，MCP 侧重接入方式。阅读 F2 详细导读与自测 →

08 · 排错记录：测试通过，为什么退出还会崩溃？

现象：D3 的 70 项测试已经输出 OK，但 Python 进程退出时仍报错：

recursive_mutex lock failed: Invalid argument

怎么理解：Python 程序可能调用底层原生库。测试断言完成后，进程还要清理资源；如果这个阶段报错，整次运行仍不能算正常结束。本次表现与 seekdb 原生依赖组合有关，具体底层根因未定位。

处理：将初次安装的 pyseekdb==1.4.0.post1 / pylibseekdb==1.4.0.post1 调整为本机验证过的兼容组合：

.venv/bin/python -m pip install 'pyseekdb==1.3.0' 'pylibseekdb==1.3.0.post5'

复验：重新运行全套测试，274 项 Python 测试通过且正常退出，没有跳过原生数据库用例；最终依赖版本写入本地版本记录。这证明该组合解决了本机遇到的现象，不意味着新版本在所有电脑上都存在同样问题。

可复用的检查方法：同时核对测试汇总和进程退出状态，并保留依赖版本与错误信息。只看到一行 OK，可能遗漏后续错误。

01 · RAG 不等于向量搜索

RAG 的核心是生成前获取外部证据。向量检索适合意思相近但措辞不同的问题；全文检索适合错误码、函数名等精确标识；元数据过滤用于限定版本、类别和访问范围；实时状态则可能需要数据库或 API 查询。

例如，“E-4012”和“E-4013”可能很相似，但错误原因不同。只看相似度不够；同理，版本号“4.2.1”不能被相近版本替代。检索方案应根据任务选择，而不是默认所有问题只走向量搜索。

02 · 六段链路：错误可能发生在哪里？

环节要解决的问题检查证据
数据准备解析、清洗、分块、补来源和版本，建立索引正确内容是否存在？分块是否丢失条件？
问题理解与改写保留实体，补必要上下文，选择检索路径改写是否丢掉错误码、时间或版本？
搜索召回向量、全文、过滤等取回候选资料目标文档是否出现在候选集合？
融合与重排多路合并、去重、重排，减少噪音正确资料是否被挤出最终上下文？

评估与反馈固定样本，分别检查各环节和最终回答修改前后是否使用同一组判断标准？

优化时先定位环节。知识库没有答案，需要补数据；已经召回但答偏了，继续提高召回率未必解决问题。

03 · 分块、Embedding 与混合检索

分块：把文档变成可检索单元。块太小可能拆掉前提和结论，太大则带入噪音。标题、来源、版本等元数据应随块保留。本次 D3 已提供 19 个预处理片段，因此没有重新实验 PDF 解析或不同分块策略。

Embedding：将文本转换为向量，用相似度寻找相关内容。文档和查询需要使用相匹配的向量模型与维度；更换模型后不能默认旧向量仍可混用。本次使用百炼 text-embedding-v4，维度为 1024。

混合检索：把语义匹配与精确词项检索结合。D3 使用 RRF 按各路排名融合结果；元数据过滤则直接限定适用范围，作用不同于“增加一个排序分数”。版本等硬条件应显式处理。

import json

from langchain_core.messages import (
    AIMessage,
    ToolMessage,
    message_chunk_to_message,
)
from langchain_core.tools import BaseTool


_REQUIRED_RESPONSE_FIELDS = ("content", "tool_calls", "invalid_tool_calls")


def _require_response_fields(response):
    """检查每个流式消息块是否具备工具循环所需的标准字段。"""
    if response is None:
        raise RuntimeError("模型返回了空响应")
    missing = [
        field
        for field in _REQUIRED_RESPONSE_FIELDS
        if not hasattr(response, field)
    ]
    if missing:
        raise RuntimeError(
            f"模型响应缺少必要字段：{', '.join(missing)}"
        )
    return response


def aggregate_stream(chunks):
    """增量聚合真实 LangChain 消息块，并拒绝结构无效的流。"""
    iterator = iter(chunks)
    try:
        response = _require_response_fields(next(iterator))
    except StopIteration:
        raise RuntimeError("模型未返回任何响应") from None

    for chunk in iterator:
        valid_chunk = _require_response_fields(chunk)
        try:
            response = response + valid_chunk
        except Exception as exc:
            raise RuntimeError(f"模型流式响应聚合失败：{exc}") from exc
        _require_response_fields(response)
    return response


def _has_nonempty_content(content):
    if isinstance(content, str):
        return bool(content.strip())
    if isinstance(content, list):
        return any(
            bool(item.strip()) if isinstance(item, str) else bool(item)
            for item in content
        )
    return False


def _validate_tool_calls(
    response,
    tools_by_name,
    *,
    require_tool_call_ids,
):
    """使用聚合后的原始 JSON 参数整批校验工具调用。"""
    invalid_tool_calls = response.invalid_tool_calls
    if invalid_tool_calls:
        raise RuntimeError(
            f"模型返回了无效工具调用 invalid_tool_calls：{invalid_tool_calls}"
        )

    tool_calls = response.tool_calls
    if not isinstance(tool_calls, list):
        raise RuntimeError("模型响应的 tool_calls 必须为列表")
    if not tool_calls:
        return []

    raw_chunks = getattr(response, "tool_call_chunks", None)
    if not isinstance(raw_chunks, list) or len(raw_chunks) != len(tool_calls):
        raise RuntimeError("模型响应缺少完整的 tool_call_chunks 原始参数")

    validated_calls = []
    seen_ids = set()
    for index, (tool_call, raw_chunk) in enumerate(
        zip(tool_calls, raw_chunks),
        start=1,
    ):
        if not isinstance(tool_call, dict) or not isinstance(raw_chunk, dict):
            raise RuntimeError(f"第 {index} 个工具调用结构无效：必须为字典")

        tool_name = tool_call.get("name")
        if not isinstance(tool_name, str) or not tool_name:
            raise RuntimeError(f"第 {index} 个工具调用的 name 必须为非空字符串")
        raw_name = raw_chunk.get("name")
        if raw_name not in (None, tool_name):
            raise RuntimeError(f"第 {index} 个工具调用名称与原始分片不一致")
        if tool_name not in tools_by_name:
            raise RuntimeError(f"模型请求了未注册的工具：{tool_name}")

        raw_args = raw_chunk.get("args")
        if not isinstance(raw_args, str):
            raise RuntimeError(f"工具 {tool_name} 的原始 args 必须是 JSON 字符串")
        try:
            tool_args = json.loads(raw_args)
        except json.JSONDecodeError as exc:
            raise RuntimeError(
                f"工具 {tool_name} 的原始 args 不是完整合法 JSON"
            ) from exc
        if not isinstance(tool_args, dict):
            raise RuntimeError(f"工具 {tool_name} 的 args 必须为 JSON 对象")

        tool_call_id = tool_call.get("id")
        raw_id = raw_chunk.get("id")
        if raw_id not in (None, tool_call_id):
            raise RuntimeError(f"第 {index} 个工具调用 ID 与原始分片不一致")
        if require_tool_call_ids:
            if not isinstance(tool_call_id, str) or not tool_call_id.strip():
                raise RuntimeError(
                    f"标准 LangChain 协议要求第 {index} 个工具调用具有非空 ID"
                )
            if tool_call_id in seen_ids:
                raise RuntimeError(
                    f"标准 LangChain 协议要求工具调用 ID 唯一：{tool_call_id}"
                )
            seen_ids.add(tool_call_id)

        validated_call = dict(tool_call)
        validated_call["args"] = tool_args
        validated_call["type"] = "tool_call"
        validated_calls.append(
            (validated_call, tools_by_name[tool_name])
        )
    return validated_calls


def _format_tool_result_message(tool_call, result):
    lines = [
        f"工具名称：{tool_call['name']}",
        f"调用参数：{tool_call['args']!r}",
    ]
    if tool_call.get("id") is not None:
        lines.append(f"调用 ID：{tool_call['id']}")
    lines.append(f"执行结果：\n\n{result}")
    return "\n".join(lines)


def _tool_message_content(result):
    """把常见工具返回值转换成 ToolMessage 可接受的内容。"""
    if isinstance(result, (str, list)):
        return result
    return json.dumps(result, ensure_ascii=False, default=str)


def _standard_assistant_message(response):
    try:
        assistant_message = message_chunk_to_message(response)
    except Exception as exc:
        raise RuntimeError(f"无法把聚合响应转换为 assistant 消息：{exc}") from exc
    if not isinstance(assistant_message, AIMessage):
        raise RuntimeError("聚合响应无法转换为标准 AIMessage")
    return assistant_message


def _standard_tool_message(tool_call, result):
    if isinstance(result, ToolMessage):
        if result.tool_call_id != tool_call["id"]:
            raise RuntimeError(
                f"工具 {tool_call['name']} 返回的 ToolMessage ID 不匹配"
            )
        return result
    return ToolMessage(
        content=_tool_message_content(result),
        tool_call_id=tool_call["id"],
    )


def _standard_error_message(tool_call, detail):
    return ToolMessage(
        content=detail,
        tool_call_id=tool_call["id"],
        status="error",
    )


def _append_skipped_tool_messages(messages, remaining_calls, reason):
    for tool_call, _tool in remaining_calls:
        messages.append(
            _standard_error_message(
                tool_call,
                f"未执行工具 {tool_call['name']}：{reason}",
            )
        )


def _callback_result(result):
    if isinstance(result, ToolMessage):
        return result.content
    return result


def _tool_input(tool, tool_call, *, legacy_user_message_fallback):
    if not legacy_user_message_fallback and isinstance(tool, BaseTool):
        return tool_call
    return tool_call["args"]


def run_tool_call_loop(
    model,
    messages,
    tools_by_name,
    max_rounds=5,
    on_tool_result=None,
    *,
    legacy_user_message_fallback=False,
):
    """执行多轮工具调用；默认使用标准 LangChain assistant/tool 协议。

    max_rounds 表示最多执行多少轮工具。执行完最后一轮后，模型仍会获得一次
    生成最终答案的机会；只有这次仍请求工具时才报告达到上限。
    """
    if (
        isinstance(max_rounds, bool)
        or not isinstance(max_rounds, int)
        or max_rounds <= 0
    ):
        raise ValueError("max_rounds 必须是正整数")

    executed_tool_rounds = 0
    while True:
        response = aggregate_stream(model.stream(messages))
        validated_calls = _validate_tool_calls(
            response,
            tools_by_name,
            require_tool_call_ids=not legacy_user_message_fallback,
        )
        if not validated_calls:
            if not _has_nonempty_content(response.content):
                raise RuntimeError("模型未返回工具调用，且最终回答为空")
            return response

        if executed_tool_rounds >= max_rounds:
            raise RuntimeError(
                f"工具调用已达到 {max_rounds} 轮上限，"
                "最终生成机会仍请求了工具"
            )

        if not legacy_user_message_fallback:
            messages.append(_standard_assistant_message(response))

        for index, (tool_call, tool) in enumerate(validated_calls, start=1):
            tool_input = _tool_input(
                tool,
                tool_call,
                legacy_user_message_fallback=legacy_user_message_fallback,
            )
            try:
                result = tool.invoke(tool_input)
            except Exception as exc:
                error_detail = f"工具 {tool_call['name']} 执行失败"
                if legacy_user_message_fallback:
                    messages.append(
                        (
                            "user",
                            _format_tool_result_message(
                                tool_call,
                                error_detail,
                            ),
                        )
                    )
                else:
                    messages.append(
                        _standard_error_message(tool_call, error_detail)
                    )
                    _append_skipped_tool_messages(
                        messages,
                        validated_calls[index:],
                        "同一批次中的前序工具执行失败",
                    )
                raise RuntimeError(
                    f"第 {index} 个工具 {tool_call['name']} 执行失败：{exc}"
                ) from exc

            if legacy_user_message_fallback:
                messages.append(
                    (
                        "user",
                        _format_tool_result_message(tool_call, result),
                    )
                )
            else:
                try:
                    messages.append(
                        _standard_tool_message(tool_call, result)
                    )
                except Exception as exc:
                    error_detail = f"工具 {tool_call['name']} 的结果消息无效"
                    messages.append(
                        _standard_error_message(tool_call, error_detail)
                    )
                    _append_skipped_tool_messages(
                        messages,
                        validated_calls[index:],
                        "同一批次中的前序工具结果消息无效",
                    )
                    raise RuntimeError(
                        f"第 {index} 个工具 {tool_call['name']} "
                        f"的结果消息无效：{exc}"
                    ) from exc

            if on_tool_result is not None:
                try:
                    on_tool_result(tool_call, _callback_result(result))
                except Exception as exc:
                    if not legacy_user_message_fallback:
                        _append_skipped_tool_messages(
                            messages,
                            validated_calls[index:],
                            "同一批次中的结果回调失败",
                        )
                    raise RuntimeError(
                        f"第 {index} 个工具 {tool_call['name']} "
                        f"的结果回调失败：{exc}"
                    ) from exc

        executed_tool_rounds += 1

先看问题：模型对象与回答对象不是一回事

llm 是客户端封装，保存调用模型所需的配置；response 是一次调用的结果。创建客户端通常并未完成问答，执行 invoke 才发送请求。

核心代码：run_demo 从输入到输出

def run_demo(llm):
    response = llm.invoke(
        [
            ("system", "你是一个简洁高效的技术助手。用中文回答，尽量用一两句话。"),

  1. 列表中的第一条 system 消息指定角色、语言和长度；第二条 user 消息才是本次问题。

  3. response.content 是内容字段，不是整个响应对象；打印它只是终端展示。

| 维度 | RAG（检索增强生成） | 直接塞文档进 Prompt |
|------|----------------------|------------------------|
| **原理** | 先用向量/关键词检索出**最相关的小片段**（如1–3个段落），再将这些片段 + 问题送入 LLM 生成答案。 | 把整篇/多篇文档（甚至整个知识库）全文或大段文本硬塞进 Prompt，让 LLM “自己找答案”。 |
| **上下文长度限制** | ✅ 规避限制：只传检索到的少量相关内容（如512 token），适配模型输入窗口。 | ❌ 极易超限：长文档 → Prompt 过长 → 被截断或报错（尤其对 4K/8K 窗口模型）。 |
| **准确性和相关性** | ✅ 更高：聚焦精准片段，减少噪声干扰，LLM 不易“胡编”无关内容。 | ❌ 易失真：大量无关文本会稀释关键信息，LLM 可能忽略重点、混淆事实，甚至幻觉。 |
| **成本与延迟** | ✅ 更低：传输/处理 token 少；可缓存/复用检索结果；支持异步预检索。 | ❌ 更高：每次请求都传巨量文本 → API 费用飙升、响应变慢、token 浪费严重。 |
| **可维护性 & 安全性** | ✅ 支持动态更新：只需更新向量库，无需改 Prompt 或重训模型；可过滤敏感/过期文档。 | ❌ 静态脆弱：文档一改就要重写 Prompt；敏感信息可能直接暴露在 prompt 日志中（安全风险！）。 |

✅ 简单类比：  
- **RAG** = 图书馆员先根据你的问题快速查出 2 本最相关的书的第3章，再帮你总结。

流式输出：先看到一部分，而不是先完成回答

stream 返回可迭代的消息块，程序边接收边显示。

invoke 与 stream 的差别

invoke 给出完整消息；stream 让调用方逐个处理增量消息块。它通常是一条持续传输的请求，不是每收到一块就重新调用一次模型，也不能保证总耗时更短。

逐行拆开 for 循环

def run_demo(llm):
    chunks = []
    for chunk in llm.stream(
        [
            ("system", "你是一个技术助手。"),
            ("user", "用三句话解释什么是向量数据库。"),
        ]
    ):
        chunks.append(chunk)
        print(chunk.content, end="", flush=True)
    print()
    return chunks
  1. chunks = [] 准备保存消息块，便于实验后分析。
  2. llm.stream(...) 发出请求，返回迭代器；for 循环在新块到达时继续。
  3. chunks.append(chunk) 保存的是块对象，而不是只有文字。
  4. end="" 不在每块后换行；flush=True 及时刷新终端缓冲区。
  5. 循环结束后单独打印换行，返回全部块。

一个 chunk 不等于一个汉字

块可能包含一段文字，也可能只包含元信息。不能用块数代替 Token 数。工具调用还可能把函数名或 JSON 参数分成多个块，所以需要先聚合完整消息，再解析和执行。

想测速度，需要分开三个时间

开始请求到首个非空文字，是首字等待；开始到完整结束，是总耗时；文本生成之外还有网络、渲染等时间。本次报告记录了整段实验耗时与块数量，没有单独测首字等待，不能据此给出首字性能结论。

变量 / 表达式类型与形状在程序中的作用
llm.stream(...)迭代器按到达顺序产出消息块；不是完整字符串。

为什么先校验整批，再逐个执行？

同一次模型响应可能请求多个工具。公共循环先检查所有请求的名称、参数 JSON 和必要 ID，再进入执行循环。这样能在后面的请求结构非法时，避免前面的工具已经产生副作用。本课程工具只查询，真实应用中还可能有写入操作。

json.loads 只解析 JSON，不执行表达式。源码拒绝未知工具名、非对象参数、不完整 JSON；标准分支还要求ID非空且不重复。不要用 eval 处理模型生成的参数。

循环什么时候停？异常谁负责？

  • 没有工具调用且正文非空：返回最终响应。
  • 没有工具调用且正文为空：报错，而不是假装完成。
  • 达到5轮工具执行后：仍请求一次模型；允许直接总结，若再次要工具则报上限。
  • 工具抛异常：记录失败消息并抛出异常，不继续把错误当成正常证据。
  • 标准分支中同批前序工具失败：还会为未执行的后续工具补充失败/跳过结果，保持消息协议完整。

回调只用于观察与记录，也可能失败；源码专门处理了该路径。因此工程代码比最小 while 伪代码长，增加的主要是边界处理。

seekdb 支持以下检索方式：

- **混合检索（Hybrid Search）**：将关键词检索与语义向量检索的结果进行融合，兼顾准确性与语义相关性。

混合检索在 seekdb 中通过 **RRF（Reciprocal Rank Fusion）算法** 实现：  
- 分别执行关键词检索和向量检索，获取各自排序的 Top-K 结果（含文档 ID 和排名位置）；  
- 对每个候选文档，按 RRF 公式计算融合得分：  
  $$\text{RRF}(d) = \sum_{i=1}^{n} \frac{1}{k + \text{rank}_i(d)}$$  
  其中 $k$ 是常数（默认为 60），$\text{rank}_i(d)$ 表示文档 $d$ 在第 $i$ 个检索结果中的排名（从 1 开始）；  
- 最终按 RRF 得分降序重排，返回融合后的结果列表。

该机制无需训练、参数少、鲁棒性强，且天然支持多路异构检索源的无偏融合。

def run_agent(agent, question: str) -> str:
    final_answer = ""
    for chunk in agent.stream({"messages": [("user", question)]}):
        for node_name, node_output in chunk.items():
            if not isinstance(node_output, dict):
                continue
            for msg in node_output.get("messages", []):
                if getattr(msg, "tool_calls", None):
                    for call in msg.tool_calls:
                        print(f"   [行动] 调用工具 '{call['name']}'，参数：{call['args']}")
                elif getattr(msg, "type", None) == "tool":
                    print(f"   [观察] 工具返回了 {msg.content.count('[文档')} 条相关文档")
                elif getattr(msg, "content", None) and node_name == "model":
                    print(msg.content, end="", flush=True)
                    final_answer += msg.content
    print()
    return final_answer
  1. agent.stream 输入新的 user 消息。
  2. 代码遍历每次返回的节点更新，node_name 表示哪个节点产生了输出。
  3. 消息包含 tool_calls 时，打印“行动”；这是结构化工具请求，不是完整的内部思考。
  4. 消息类型为 tool 时，打印“观察”；课程按内容中的“[文档”计数，只是展示用。
  5. model 节点返回有内容且无工具调用的消息时，累加最终答案。

D1-3 的 stream 是模型文本块；此处默认消费 Agent 节点更新。虽然都使用 for 循环，事件粒度不同。

问题 3：seekdb 支持哪些检索方式？混合检索的原理是什么？
============================================================
   [行动] 调用工具 'search_knowledge_base'，参数：{'query': 'seekdb 检索方式 混合检索原理'}
   [观察] 工具返回了 3 条相关文档
SeekDB 支持以下三种检索方式：

1. **关键词检索（Keyword Search）**：基于传统倒排索引，支持分词、布尔逻辑（AND/OR/NOT）、通配符、模糊匹配等，召回精准匹配的结构化或半结构化文本片段。

2. **语义向量检索（Vector Search）**：将查询和文档嵌入为高维向量，通过近似最近邻（ANN）算法（如 HNSW 或 FAISS）计算余弦相似度，实现语义层面的相关性匹配，对同义、 paraphrase 和上下文理解更鲁棒。

3. **混合检索（Hybrid Search）**：  
   - **原理**：采用 **RRF（Reciprocal Rank Fusion）** 算法融合关键词与向量检索的排序结果。  
     - 对每个检索通道分别获取 Top-K 结果（如 Top-50），记录各条目在各自排序中的位置（rank，从 1 开始计数）；  
     - 计算 RRF 分数：`score = 1 / (k + rank)`，其中 `k` 是常数（默认通常为 60）；  
     - 合并所有结果，按 RRF 分数加总后重排序，兼顾关键词的精确性与向量的语义泛化能力。  
   - 优势：无需训练、零样本融合、鲁棒性强，能有效缓解单一检索的偏差（如向量漏检关键词强匹配项，或关键词无法理解隐含语义）。

注：SeekDB 的混合检索默认启用 RRF，也支持自定义融合策略（如加权线性融合），但 RRF 是其推荐且开箱即用的核心机制。

def run_agent(agent, question: str) -> str:
    final_answer = ""
    for chunk in agent.stream({"messages": [("user", question)]}):
        for node_name, node_output in chunk.items():
            if not isinstance(node_output, dict):
                continue
            for msg in node_output.get("messages", []):
                if getattr(msg, "tool_calls", None):
                    for call in msg.tool_calls:
                        print(f"   [行动] 调用工具 '{call['name']}'，参数：{call['args']}")
                elif getattr(msg, "type", None) == "tool":
                    print(f"   [观察] 工具返回了 {msg.content.count('[文档')} 条相关文档")
                elif getattr(msg, "content", None) and node_name == "model":
                    print(msg.content, end="", flush=True)
                    final_answer += msg.content
    print()
    return final_answer

第一步：切分函数逐行读

def chunk_document(text: str, chunk_size: int = 200, overlap: int = 30) -> list[str]:
    """将长文档切成带重叠的片段。"""
    if chunk_size <= 0:
        raise ValueError("chunk_size 必须大于 0")
    if overlap < 0 or overlap >= chunk_size:
        raise ValueError("overlap 必须大于等于 0 且小于 chunk_size")
    chunks = []
    start = 0
    while start < len(text):
        chunks.append(text[start : start + chunk_size].strip())
        start += chunk_size - overlap
    return [chunk for chunk in chunks if chunk]
  1. 先验证 chunk_size 大于0，overlap 位于 [0, chunk_size)；否则步长可能不前进。
  2. start 指向片段起点，切片右边界不包含在结果中。
  3. 每次 start 增加 chunk_size - overlap。默认200 - 30 = 170，相邻片段保留30字符重叠。
  4. strip 去除片段边缘空白，最后过滤空字符串。

这里计算的是 Python 字符串长度，不是模型 Token。固定长度切分也不理解句子和段落边界。

def chunk_document(text: str, chunk_size: int = 200, overlap: int = 30) -> list[str]:
    """将长文档切成带重叠的片段。"""
    if chunk_size <= 0:
        raise ValueError("chunk_size 必须大于 0")
    if overlap < 0 or overlap >= chunk_size:
        raise ValueError("overlap 必须大于等于 0 且小于 chunk_size")
    chunks = []
    start = 0
    while start < len(text):
        chunks.append(text[start : start + chunk_size].strip())
        start += chunk_size - overlap
    return [chunk for chunk in chunks if chunk]

  • query 是关键词/全文检索配置，where_document 给出文档内容条件。

  • 两路各自 n_results=5，是进入融合的候选数量；最外层 n_results=3，是最终输出数量。
  • rank={"rrf":{}} 选择按排名融合。本例不是对两个原始距离直接求和。

用数字手算 RRF

假设两路等权、rank_constant=60、排名从1开始：
文档A：全文第1，向量第1
score(A) = 1/(60+1) + 1/(60+1) ≈ 0.03279
文档B：只在向量第2
score(B) = 1/(60+2) ≈ 0.01613

这是本次报告数值所对应的计算示例。RRF 使用候选排名，绕开原始分数量纲不同的问题；不证明排序必然正确，也不能仅凭四舍五入后的一个分数唯一倒推每路排名。

把笔记写进文件，不意味着模型权重发生变化。文件里的信息需要被正确读取和使用，才会影响后续回答。

追踪一条周报规则的完整旅程

假设用户提出：“周报先写结论，再列风险，不要超过三段。”下面是一个经验复用的教学示例，不表示所有助手都会自动执行这些步骤。

  1. 确认与保存：把明确的偏好写入可持久保存的记录，并标明只适用于周报，避免误用到所有文章。
  2. 按任务召回：下次收到“写周报”的请求时，找到这条规则，而不是加载全部历史。
  3. 放入当前上下文：将规则与本周工作事实一起交给模型。存储中的信息只有被提供给这次调用，才有机会发挥作用。
  4. 执行并核对：检查输出是否先给结论、是否列出风险、是否满足篇幅要求。读到规则也不保证一定遵守。
  5. 纠错与更新：如果用户改为“先列风险”，更新适用规则，处理旧版本；不要让两条冲突要求长期并存。
失败时，沿链路找原因

没有保存 → 下次没有来源；保存但没召回 → 来源存在但这次看不到；召回了旧规则 → 数据过期；提供了正确规则仍没执行 → 继续检查理解和执行。

因此，“越用越好用”依赖整条链路。它不意味着每次对话都在训练模型，也不意味着记录越多越好。

02
这一章的核心

语言流畅不等于事实可靠。课程提醒我们：除了模型能力，还要检查它是否拿到了正确、及时、与任务相关的数据。

大模型是怎样生成文字的？

可以先把它理解为：根据已经看到的上下文，预测接下来可能出现的 Token，并一步步生成内容。它学到的语言和知识规律很强，但生成过程并不自动完成事实核验。

示例 · “天空是……”

模型可以根据常见表达续写“蓝色的”。但要回答“此刻窗外的天空是什么颜色”，还需要当前地点和实际天气等信息。

三个局限，三种数据检查

01 / 幻觉

听起来合理，事实却不对

例如编出不存在的文献。检查有没有可靠来源、是否检索正确、回答是否忠于证据。

02 / 知识截止

没有自动获得最新信息

例如把旧产品规则当成最新政策。检查来源日期，必要时接入实时数据。

03 / 个性化盲区

不了解你的具体背景

例如建议听起来正确，却不适合你的项目。补充实际目标、约束和业务资料。

阅读时保留一个边界：课程强调“补数据”的价值；这不意味着所有错误都只由缺数据造成。模型理解、推理、检索和提示方式也需要分别验证。

完整排查：退货政策为什么答错了？

虚构案例 · 只用于理解排查方法

助手说“签收后 30 天内都能退”。提供的当前政策实际上写着“7 天内且满足商品条件”，订单已经签收 10 天。数字仅为教学设定，不是任何商家的实际政策。

  1. 检查有没有证据：本次输入是否包含政策？如果没有，回答可能没有对应依据，应先检索或补充资料。
  2. 检查版本与适用范围：拿到的是当前政策还是旧政策？是否适用于这个商品、地区和订单？资料存在不等于适用。
  3. 检查必要事实：签收时间、商品类别和相关条件是否齐全？缺少事实时，应查询或澄清，而不是补猜。
  4. 检查理解与推断：若正确条款和订单事实已提供，仍回答“30 天”，就要检查模型是否误读、忽略条件或产生不受证据支持的内容。
  5. 验证改动：保留问题和已核实事实，对照修改前后的回答及依据；检查它是否说明条件和不确定性，不能只看语气是否更肯定。

这套顺序把“模型错了”拆成可检查的环节。补资料解决不了所有错误，但能帮助定位问题发生在哪里。

两个必知词：Token 与上下文

Token：处理文本的单位

文字会被切成小片段交给模型处理。一个 Token 不固定等于一个汉字或一个单词，具体取决于分词器。

API 用量通常区分输入 Token 和输出 Token。

上下文窗口：这次能看到多少

模型一次处理的内容有长度上限，历史消息、工具结果和参考资料都可能占用空间；具体限制取决于模型。

窗口很大，也不等于所有内容都能被有效利用。

类比 · 桌面与档案柜

上下文像桌面：放着当前任务要用的材料。长期记忆像档案柜：保存更多资料，需要的时候再找出来放到桌面上。桌面变大，不会自动替你整理档案柜。

当前上下文与长期记忆，区别在哪里？

当前上下文是这次调用实际可见的材料。长期记忆是模型之外保存的信息，需要在适当时机找出、筛选并加入上下文。二者不是同一个容量，也不是同一段生命周期。

例如，周报偏好已经写在文件里，但新对话没有读取它，这次模型就未必能按该偏好工作。反过来，在当前对话粘贴了一条偏好，也不代表产品会永久保存。

管理上下文不是“越塞越多”：应优先保留相关、可靠且适用的信息，处理冲突和过期内容，并在空间有限时选择或压缩材料。

  2. 资料已经存在吗？存在的话，为什么没有拿到或用对？
  3. 补上可靠资料后，能否通过可核验的问题检验改善？

一条完整任务：查清条件，再申请退货

贯穿案例 · 未连接真实订单系统

用户：“这笔订单能退吗？如果可以，帮我申请。”这次不仅需要解释政策，还需要查询实际状态并核对操作结果。

  1. 明确对象：确定是哪笔订单；必要信息缺失时先询问。历史记录可以提供线索，但订单当前状态要重新核实。
  2. 查找依据：检索适用的退货政策，并查询签收时间、商品信息和当前订单状态。
  3. 判断条件：将事实与条款逐项对照；有歧义时继续查证或澄清，而不是跳到提交。
  4. 执行操作：满足条件并具备所需授权后，调用申请工具。按实际业务流程处理确认步骤。
  5. 观察返回：检查服务返回的是已受理、待处理还是失败；用请求状态或后续查询核对，不能把“已发送请求”当成“已办结”。
  6. 处理下一步：失败时根据原因补充信息或交接；成功时报告已验证的状态和后续事项。

这就是判断、行动、观察再判断的循环。ReAct 将推理与行动交替组织；显式工作流则预先规定节点和条件。实际系统可以结合两者，并设置停止和异常处理条件。

四类能力，用同一个客服例子区分

RAG 查资料

先检索相关知识，再将证据交给模型回答。

客服例子：从当前版本的退货政策中，查到申请期限。

关键问题：资料是否完整、最新、可检索？

Memory 记住与召回

保存有用的事实、偏好和经历，并在需要时取出。

客服例子：记住用户此前已提供订单信息，避免重复询问。

关键问题：记什么、保存多久、何时更新？

Skill 按方法办事

把某类任务的步骤、规则与示例整理为可复用方法。

客服例子：先核验条件、再说明政策、最后给出操作步骤。

关键问题：方法是否清楚，是否适合当前任务？

MCP 标准化接入

让客户端与服务端按共同协议连接工具、资源和提示模板。

客服例子：通过标准接口接入订单查询工具。

关键问题：接入什么能力，允许访问什么？

四个名词，不是四个必装组件

在上述任务中主要解决什么不等于什么
RAG 检索政策让回答获得相关证据不保证资料正确，也不直接执行退货
Memory 召回订单背景复用有用历史信息历史状态不等于实时订单状态
Skill 规定处理步骤复用方法、规则和示例流程说明不等于工具已执行
MCP 接入订单能力规范工具、资源等的接入方式协议不替代权限、业务规则或结果验证

它们处于不同层面，可能配合，也可能不全需要。只回答政策问题时，检索和生成或许足够；一次性任务未必需要长期记忆；工具也可以直接通过 API 接入，并非必须使用 MCP。

场景判断：工具调用结束，任务就成功了吗？

退货申请工具返回“请求超时”，但助手已经说“申请成功”。问题出在哪里？应立即重复提交吗？

查看参考分析

超时意味着尚未确认结果，不能报告成功，也不能仅凭超时断言服务没有受理。应优先查询请求或订单状态；确需重试时遵守服务的防重复提交机制。关键是验证外部状态，而不是相信助手的措辞。
