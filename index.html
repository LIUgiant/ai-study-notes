02 · 已有 Qwen 和 DeepSeek，API 怎么用？

本次使用的是阿里云百炼的 Qwen API，以及 DeepSeek 官网 API。调用时不只有 Key：还要匹配对应服务商的接口地址和模型名。密钥保存在本机 code/.env，不写入公开笔记。

操作分为三步：先准备配置位置，再填入两家的 Key，最后运行独立的在线检查脚本。课程原版配置没有直接接入本次 DeepSeek 变量，因此由单独的检查脚本完成适配。

# 在课程仓库根目录运行；这条命令会发起真实模型请求
.venv/bin/python learning/task1/check_api.py --run-online

两次请求都只输入“只回复 OK”，各调用一次、不自动重试，每次最大输出 16 Token。下面是已保存结果的摘要，不是重新发起的请求。

服务商 / 当次模型返回内容输入 / 输出 Token
百炼 / qwen-plusOK11 / 1
DeepSeek / deepseek-flashOK7 / 1

这能说明什么？当次使用的密钥、地址和请求格式能够完成基本对话调用。两次响应合计 20 Token；未查询账单，不推算实际扣费。

还不能说明什么？回复“OK”不代表复杂问答准确，也没有验证 Embedding、工具调用或完整 Agent 流程。模型名和结果只对应上述实践日期。

03 · Shell、Python、Git 自检有什么用？

Shell 用来执行命令，Python 用来运行课程程序，Git 用来管理代码版本。它们是不同层面的准备：能打开终端，不等于依赖已安装；能安装依赖，也不等于程序能正常运行。

# 基础版本检查
zsh --version
python3 --version
git --version

# 检查课程虚拟环境及其依赖
.venv/bin/python --version
.venv/bin/python -m pip check

本机默认 Python 为 3.12.13，课程使用项目内独立的 Python 3.11.15 环境，系统版本未改动。独立环境让课程依赖与其他项目分开；执行课程代码时需要使用对应解释器。

Git 已核对版本、当前分支和工作区状态。依赖检查返回 No broken requirements found.；兼容问题处理后，完整课程测试共 15 组、274 项 Python 测试通过，另有 7 项贡献者工具的 Node 测试通过。

这些是运行条件和现有测试的验证，不等于已学完这些章节，也不保证所有真实场景都正确。

04 · F0：文件里保存了经验，模型就“学会”了吗？

不一定。这里要分开两件事：训练可以改变模型参数；把偏好或规则写进文件，改变的是模型可以读取的外部信息。文件存在，并不代表每次回答都会用到它。

例子：周报先写结论

把“周报先写结论”保存为规则 → 下次写周报时读到这条规则 → 放入当前上下文 → 按规则生成 → 检查是否执行。若只完成第一步，后续仍可能没有效果。

因此，经验积累包括保存、召回、使用和维护。错误或过期的规则需要更新，不能只靠不断增加文件。阅读 F0 详细导读与自测 →

05 · F1：模型回答错了，应该先检查什么？

模型根据上下文生成文字，流畅的表达本身不是事实依据。遇到不可靠回答时，可以先分辨缺的是哪类信息：

  • 事实依据不足：关键说法有没有可核对的资料？
  • 信息过时：资料的日期、版本是否适合当前问题？
  • 背景缺失：模型是否知道本次任务所需的用户或业务条件？

例如，询问退货条件时，如果模型拿到的是旧政策，回答再清楚也可能不适用。补充当前政策后，还要继续核对它是否正确理解条款，而不是认为“有资料就一定对”。

Token 与上下文：Token 是模型处理文本的片段单位，与汉字数量没有固定对应关系。上下文像容量有限的工作台，要放入当前任务需要的信息；长聊天记录也不自动等于跨会话的持久记忆。阅读 F1 详细导读与自测 →

06 · F2：用一个退货场景串起四类能力

假设用户问：“这笔订单能退吗？如果可以，帮我申请。”这不只是回答知识题，还涉及查询、判断和行动。以下是概念示例，本次没有连接真实订单系统。

  1. 先找到依据（RAG）：检索当前有效的退货政策，把相关条款交给模型参考。
  2. 补足已有背景（Memory）：召回用户此前提供的订单背景，避免重复询问；订单当前状态仍需查询，不能把旧记录当作最新事实。
  3. 按流程处理（Skill）：先核对订单和条件，再解释判断依据，在需要时取得确认，最后提交申请并核对结果。
  4. 接入外部能力（MCP）：如果订单服务提供 MCP 接口，可通过统一协议暴露查询、申请等工具。MCP 负责接入规范，业务规则和权限仍要另行处理。

模型观察查询结果、决定下一步、调用工具，再观察返回结果，形成持续的任务循环。若申请失败，就需要根据错误继续处理，而不是只生成一句“已成功”。

这四项不是同一种东西，也不是每个 Agent 都必须全部具备。RAG 侧重找证据，Memory 侧重历史信息的保留与召回，Skill 侧重可复用方法，MCP 侧重接入方式。阅读 F2 详细导读与自测 →

07 · 补充探索：离线评测不调用模型，在测什么？

实际提问是：“跑程序后，返回什么结果？这里不需要大模型吗？”对本次运行的 D3/P5 离线入口，答案是：使用固定样例和模拟组件，运行后生成报告，不需要调用真实大模型。

固定输入让预期行为可以重复检查。例如，给出一个带版本号或错误码的问题，检索是否保留关键标识，是否找到目标资料，证据不足时是否按预期处理。

这个入口除离线评测外，还会运行课程测试和文档检查。报告分别写入 learning/task1/reports/，不是在网页中直接与模型聊天。

08 · 排错记录：测试通过，为什么退出还会崩溃？

现象：D3 的 70 项测试已经输出 OK，但 Python 进程退出时仍报错：

recursive_mutex lock failed: Invalid argument

怎么理解：Python 程序可能调用底层原生库。测试断言完成后，进程还要清理资源；如果这个阶段报错，整次运行仍不能算正常结束。本次表现与 seekdb 原生依赖组合有关，具体底层根因未定位。

处理：将初次安装的 pyseekdb==1.4.0.post1 / pylibseekdb==1.4.0.post1 调整为本机验证过的兼容组合：

.venv/bin/python -m pip install 'pyseekdb==1.3.0' 'pylibseekdb==1.3.0.post5'

复验：重新运行全套测试，274 项 Python 测试通过且正常退出，没有跳过原生数据库用例；最终依赖版本写入本地版本记录。这证明该组合解决了本机遇到的现象，不意味着新版本在所有电脑上都存在同样问题。

可复用的检查方法：同时核对测试汇总和进程退出状态，并保留依赖版本与错误信息。只看到一行 OK，可能遗漏后续错误。

01 · RAG 不等于向量搜索

RAG 的核心是生成前获取外部证据。向量检索适合意思相近但措辞不同的问题；全文检索适合错误码、函数名等精确标识；元数据过滤用于限定版本、类别和访问范围；实时状态则可能需要数据库或 API 查询。

例如，“E-4012”和“E-4013”可能很相似，但错误原因不同。只看相似度不够；同理，版本号“4.2.1”不能被相近版本替代。检索方案应根据任务选择，而不是默认所有问题只走向量搜索。

02 · 六段链路：错误可能发生在哪里？

环节要解决的问题检查证据
数据准备解析、清洗、分块、补来源和版本，建立索引正确内容是否存在？分块是否丢失条件？
问题理解与改写保留实体，补必要上下文，选择检索路径改写是否丢掉错误码、时间或版本？
搜索召回向量、全文、过滤等取回候选资料目标文档是否出现在候选集合？
融合与重排多路合并、去重、重排，减少噪音正确资料是否被挤出最终上下文？
组织与生成提供证据、约束回答、核对引用每条结论是否受到证据支持？
评估与反馈固定样本，分别检查各环节和最终回答修改前后是否使用同一组判断标准？

优化时先定位环节。知识库没有答案，需要补数据；已经召回但答偏了，继续提高召回率未必解决问题。

03 · 分块、Embedding 与混合检索

分块：把文档变成可检索单元。块太小可能拆掉前提和结论，太大则带入噪音。标题、来源、版本等元数据应随块保留。本次 D3 已提供 19 个预处理片段，因此没有重新实验 PDF 解析或不同分块策略。

Embedding：将文本转换为向量，用相似度寻找相关内容。文档和查询需要使用相匹配的向量模型与维度；更换模型后不能默认旧向量仍可混用。本次使用百炼 text-embedding-v4，维度为 1024。

混合检索：把语义匹配与精确词项检索结合。D3 使用 RRF 按各路排名融合结果；元数据过滤则直接限定适用范围，作用不同于“增加一个排序分数”。版本等硬条件应显式处理。

06 · 实验三：跑通 Agent 的工具循环

复用课程 d3_2_agentic_rag.ask_agent，通过本地适配器把生成服务换成百炼 qwen-plus，保留课程工具定义和 seekdb 混合搜索。设置最多两轮工具执行，无自动网络重试。

  1. 向模型提供问题与检索工具说明。
  2. 模型选择调用 search_knowledge_base。
  3. 本地程序执行检索，把结果作为工具消息返回。
  4. 模型根据结果生成答案，或继续检索；达到上限则停止。

实际观察：版本兼容性和错误码问题各触发一次搜索；“你好”没有触发搜索。说明这三条样例中的工具路由和回传流程已跑通，但不代表任意复杂问题都可靠。

检索正确，答案仍可能越界

初次兼容性回答引入了资料中没有的命令、参数和文档编号；错误码回答也增加了未经资料支持的操作细节。输出还受到长度上限影响。因此这次只确认调用链路成功，不能把初次答案判为质量通过。

后续固定同一批检索证据，将提示改为“只用证据、未说明的细节明确指出、逐条引用、短回答”，再调用两次模型做生成对照。以下展示改进后的实际输出，而非经过润色的标准答案。

OB-4.2.1 版本和旧版本兼容吗？

OB-4.2.1 与 OB-4.1.x 向后兼容，但不兼容 OB-3.x 系列[结果 1]；跨大版本（如 OB-3.x 到 OB-4.x）需用官方迁移工具，不可直接升级[结果 3]。

遇到 E-4012 错误怎么解决？

E-4012 是数据库连接池耗尽错误。解决方法：(1) 增大 max_connections；(2) 检查应用是否存在连接泄漏，确保及时关闭连接；(3) 使用连接池中间件，并设置连接最大生命周期（如30分钟）和空闲回收（如5分钟）；(4) 高峰前预热连接池。[结果 1][结果 2]

07 · 从实验得到的结论

  • 检索与生成要分开评估。命中文档不代表回答忠于证据，生成模型可能继续补写。
  • 指标本身也需要检查。片段关键词判断简单易运行，但可能低估相关结果。
  • 增强检索不是无条件获胜。需要固定数据、清楚的判分口径和更多样例。
  • Agentic 的关键是运行时决策。本次看到模型决定是否检索；没有展示多跳补搜和复杂恢复能力。
  • 小实验不是生产结论。本次未做重复统计、RAGAS、流式首字延迟或完整权限验收。

Agent 的经验，从哪里来？

01
这一章的核心

课程以 OpenClaw 为例：把偏好、规则和经验保存下来，在下一次任务中重新读取，Agent 才有机会持续利用过去的经验。

先分清两件事

模型本身的学习训练过程改变模型参数
本章讨论的经验积累保存外部数据，再放入上下文

把笔记写进文件，不意味着模型权重发生变化。文件里的信息需要被正确读取和使用，才会影响后续回答。

追踪一条周报规则的完整旅程

假设用户提出：“周报先写结论，再列风险，不要超过三段。”下面是一个经验复用的教学示例，不表示所有助手都会自动执行这些步骤。

  1. 确认与保存：把明确的偏好写入可持久保存的记录，并标明只适用于周报，避免误用到所有文章。
  2. 按任务召回：下次收到“写周报”的请求时，找到这条规则，而不是加载全部历史。
  3. 放入当前上下文：将规则与本周工作事实一起交给模型。存储中的信息只有被提供给这次调用，才有机会发挥作用。
  4. 执行并核对：检查输出是否先给结论、是否列出风险、是否满足篇幅要求。读到规则也不保证一定遵守。
  5. 纠错与更新：如果用户改为“先列风险”，更新适用规则，处理旧版本；不要让两条冲突要求长期并存。
失败时，沿链路找原因

没有保存 → 下次没有来源；保存但没召回 → 来源存在但这次看不到；召回了旧规则 → 数据过期；提供了正确规则仍没执行 → 继续检查理解和执行。

因此，“越用越好用”依赖整条链路。它不意味着每次对话都在训练模型，也不意味着记录越多越好。

为什么不能只管“存得多”？

写入质量

误会、过期规则和未经确认的推断也可能被保存。需要审查、纠正和更新。

召回质量

存了不等于用到了。信息越来越多时，要找到当前相关的内容，避免全部挤进上下文。

F1 · 大模型的本质与边界

回答很流畅，为什么还会错？

沿着一个错误回答，检查资料有没有拿到、是否适用、有没有被正确理解。

02
这一章的核心

语言流畅不等于事实可靠。课程提醒我们：除了模型能力，还要检查它是否拿到了正确、及时、与任务相关的数据。

大模型是怎样生成文字的？

可以先把它理解为：根据已经看到的上下文，预测接下来可能出现的 Token，并一步步生成内容。它学到的语言和知识规律很强，但生成过程并不自动完成事实核验。

示例 · “天空是……”

模型可以根据常见表达续写“蓝色的”。但要回答“此刻窗外的天空是什么颜色”，还需要当前地点和实际天气等信息。

三个局限，三种数据检查

01 / 幻觉

听起来合理，事实却不对

例如编出不存在的文献。检查有没有可靠来源、是否检索正确、回答是否忠于证据。

02 / 知识截止

没有自动获得最新信息

例如把旧产品规则当成最新政策。检查来源日期，必要时接入实时数据。

03 / 个性化盲区

不了解你的具体背景

例如建议听起来正确，却不适合你的项目。补充实际目标、约束和业务资料。

阅读时保留一个边界：课程强调“补数据”的价值；这不意味着所有错误都只由缺数据造成。模型理解、推理、检索和提示方式也需要分别验证。

完整排查：退货政策为什么答错了？

虚构案例 · 只用于理解排查方法

助手说“签收后 30 天内都能退”。提供的当前政策实际上写着“7 天内且满足商品条件”，订单已经签收 10 天。数字仅为教学设定，不是任何商家的实际政策。

  1. 检查有没有证据：本次输入是否包含政策？如果没有，回答可能没有对应依据，应先检索或补充资料。
  2. 检查版本与适用范围：拿到的是当前政策还是旧政策？是否适用于这个商品、地区和订单？资料存在不等于适用。
  3. 检查必要事实：签收时间、商品类别和相关条件是否齐全？缺少事实时，应查询或澄清，而不是补猜。
  4. 检查理解与推断：若正确条款和订单事实已提供，仍回答“30 天”，就要检查模型是否误读、忽略条件或产生不受证据支持的内容。
  5. 验证改动：保留问题和已核实事实，对照修改前后的回答及依据；检查它是否说明条件和不确定性，不能只看语气是否更肯定。

这套顺序把“模型错了”拆成可检查的环节。补资料解决不了所有错误，但能帮助定位问题发生在哪里。

两个必知词：Token 与上下文

Token：处理文本的单位

文字会被切成小片段交给模型处理。一个 Token 不固定等于一个汉字或一个单词，具体取决于分词器。

API 用量通常区分输入 Token 和输出 Token。

上下文窗口：这次能看到多少

模型一次处理的内容有长度上限，历史消息、工具结果和参考资料都可能占用空间；具体限制取决于模型。

窗口很大，也不等于所有内容都能被有效利用。

类比 · 桌面与档案柜

上下文像桌面：放着当前任务要用的材料。长期记忆像档案柜：保存更多资料，需要的时候再找出来放到桌面上。桌面变大，不会自动替你整理档案柜。

当前上下文与长期记忆，区别在哪里？

当前上下文是这次调用实际可见的材料。长期记忆是模型之外保存的信息，需要在适当时机找出、筛选并加入上下文。二者不是同一个容量，也不是同一段生命周期。

例如，周报偏好已经写在文件里，但新对话没有读取它，这次模型就未必能按该偏好工作。反过来，在当前对话粘贴了一条偏好，也不代表产品会永久保存。

管理上下文不是“越塞越多”：应优先保留相关、可靠且适用的信息，处理冲突和过期内容，并在空间有限时选择或压缩材料。

遇到“AI 不好用”，先问这三句

  1. 它缺少的是事实、实时信息，还是任务背景？
  2. 资料已经存在吗？存在的话，为什么没有拿到或用对？
  3. 补上可靠资料后，能否通过可核验的问题检验改善？
有了 RAG，就不会产生幻觉了吗？

不能这样保证。检索可能拿错资料，资料可能过时，模型也可能误读。仍然需要检查来源、引用与答案之间的对应关系。

聊天产品能记住我，是否说明模型天然有永久记忆？

产品可以在模型之外保存历史和用户信息，并在后续调用中提供给模型。要区分“产品提供记忆功能”和“单次模型调用本身保存记忆”。

场景判断：还需要继续补资料吗？

当前政策已明确写明申请期限，订单日期也已核实，但回答引用了正确条款，却给出与条款矛盾的结论。仅仅增加更多文档，能保证解决问题吗？

查看参考分析

不能。已有证据与结论不一致，应检查条件理解和推理过程，并用明确事实复核结论。继续堆文档可能增加干扰。还应检查资料是否存在例外条款，避免只凭片段下结论。

F2 · AI Agent 全景图

从“回答问题”到“执行任务”

沿着一次退货申请，理解资料、记忆、方法和工具如何配合。

03
这一章的核心

Agent 把模型推理、规划、记忆与工具调用组织起来。它可以查看行动结果，再决定接下来做什么。

一条完整任务：查清条件，再申请退货

贯穿案例 · 未连接真实订单系统

用户：“这笔订单能退吗？如果可以，帮我申请。”这次不仅需要解释政策，还需要查询实际状态并核对操作结果。

  1. 明确对象：确定是哪笔订单；必要信息缺失时先询问。历史记录可以提供线索，但订单当前状态要重新核实。
  2. 查找依据：检索适用的退货政策，并查询签收时间、商品信息和当前订单状态。
  3. 判断条件：将事实与条款逐项对照；有歧义时继续查证或澄清，而不是跳到提交。
  4. 执行操作：满足条件并具备所需授权后，调用申请工具。按实际业务流程处理确认步骤。
  5. 观察返回：检查服务返回的是已受理、待处理还是失败；用请求状态或后续查询核对，不能把“已发送请求”当成“已办结”。
  6. 处理下一步：失败时根据原因补充信息或交接；成功时报告已验证的状态和后续事项。

这就是判断、行动、观察再判断的循环。ReAct 将推理与行动交替组织；显式工作流则预先规定节点和条件。实际系统可以结合两者，并设置停止和异常处理条件。

四类能力，用同一个客服例子区分

RAG 查资料

先检索相关知识，再将证据交给模型回答。

客服例子：从当前版本的退货政策中，查到申请期限。

关键问题：资料是否完整、最新、可检索？

Memory 记住与召回

保存有用的事实、偏好和经历，并在需要时取出。

客服例子：记住用户此前已提供订单信息，避免重复询问。

关键问题：记什么、保存多久、何时更新？

Skill 按方法办事

把某类任务的步骤、规则与示例整理为可复用方法。

客服例子：先核验条件、再说明政策、最后给出操作步骤。

关键问题：方法是否清楚，是否适合当前任务？

MCP 标准化接入

让客户端与服务端按共同协议连接工具、资源和提示模板。

客服例子：通过标准接口接入订单查询工具。

关键问题：接入什么能力，允许访问什么？

四个名词，不是四个必装组件

在上述任务中主要解决什么不等于什么
RAG 检索政策让回答获得相关证据不保证资料正确，也不直接执行退货
Memory 召回订单背景复用有用历史信息历史状态不等于实时订单状态
Skill 规定处理步骤复用方法、规则和示例流程说明不等于工具已执行
MCP 接入订单能力规范工具、资源等的接入方式协议不替代权限、业务规则或结果验证

它们处于不同层面，可能配合，也可能不全需要。只回答政策问题时，检索和生成或许足够；一次性任务未必需要长期记忆；工具也可以直接通过 API 接入，并非必须使用 MCP。

Naive RAG 与 Agentic RAG

固定检索流程

检索一次，整理上下文，生成答案。流程简单、容易理解。

可以调整的检索流程

判断查哪里、是否补查、是否换关键词。更灵活，也增加了调用次数和控制难度。

先用任务需求决定复杂度。更多步骤不自动意味着更好的结果，还要比较正确性、耗时与成本。

给“记忆”再分一分工

类别容易理解的含义例子
工作记忆当前任务正在使用的状态和材料本次对话与刚查到的结果
语义记忆事实和稳定偏好用户喜欢先看简短结论

退货申请工具返回“请求超时”，但助手已经说“申请成功”。问题出在哪里？应立即重复提交吗？

再想一步：若工具返回的是“申请已受理”，也只能报告已受理，不能说“退款已到账”。
